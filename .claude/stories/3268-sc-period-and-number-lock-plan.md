# SC Period-of-Performance Mod Tracking + SC Number Lock on Awarded Agreements

## Goal

Extend the direct-apply + tracked-edit pattern shipped in PR #6536 to cover two gaps in `ServicesComponentService.update()`: (1) track Services Component period-of-performance edits as "Modified LOE" contract-modification edits on Awarded agreements, and (2) prevent the SC's own number from being changed at all once an agreement is Awarded.

## Requirements

1. Editing a Services Component's period of performance (`period_start`/`period_end`) on an Awarded agreement should trigger/track a "Modified LOE" type contract-modification edit.
2. Users should NOT be able to edit the SC number (the "Services Component Select" control) on Awarded agreements.

## Technical Details

### Approach

**Requirement 1 — SC period-of-performance tracked as "Modified LOE"**

`ServicesComponentService.update()` (`backend/ops_api/ops/services/services_component.py`, lines ~130-176) currently has **zero** contract-modification tracking logic — unlike `create()`/`delete()`, which already call `ContractModificationEditService`. `period_start`/`period_end` are real, directly-updatable `Mapped[Optional[date]]` columns on `ServicesComponent` (`backend/models/services_components.py`), and today a period edit on an Awarded agreement applies silently through `update()`'s generic `self.db_session.merge(ServicesComponent(**updated_fields))` with no tracking at all.

`ModificationEditType.MODIFIED_LOE` already exists (`backend/models/contract_modification_edits.py`) and is exactly what `record_services_component_add`/`record_services_component_delete` already use — so "Modified LOE" classification for an SC edit has direct precedent, nothing new to invent there.

Add `record_services_component_edit(services_component, field, old_value, new_value, user_id)` to `ContractModificationEditService` (`backend/ops_api/ops/services/contract_modification_edits.py`), modeled directly on `record_direct_edit` (lines ~109-142) but keyed on `services_component_id` instead of `budget_line_item_id`:
- Needs its own `_pending_for_services_component(services_component_id, field=None)` lookup mirroring `_pending_for_budget_line` (lines ~233-246), filtering `services_component_id == ... AND budget_line_item_id.is_(None) AND agreement_mod_id.is_(None)`.
- Same merge-with-pending / net-zero-discard / flush-then-`IntegrityError`-catch pattern as `record_direct_edit`.
- `_latest_per_budget_line_field` (lines ~291-312) already keys SC rows by `("sc", services_component_id)` and is field-aware, so a `period_start` edit and a `period_end` edit on the same SC naturally stay as two distinct cards without further changes there — the reporting/listing path is already SC-edit-aware.

Call the new method from `ServicesComponentService.update()`: before the merge/commit, if `agreement_tracks_contract_modifications(services_component.agreement)` is true and `period_start`/`period_end` changed, call the new method per changed field using `get_current_user().id` — same shape as `record_direct_edit`'s old/new value convention. Note `agreement_tracks_contract_modifications` is **not currently imported** in `services_component.py` (only reached indirectly via `sc_requires_approval_gate`) — add the import.

A new partial unique index, mirroring `ix_contract_modification_edit_one_pending_bli_field`, is needed as `ix_contract_modification_edit_one_pending_sc_field` on `(services_component_id, field)` WHERE `agreement_mod_id IS NULL AND services_component_id IS NOT NULL AND budget_line_item_id IS NULL` — the `budget_line_item_id IS NULL` clause avoids collision with the SC-add/delete rows that already use `services_component_id` with `field` values like `"services_component_create"`/`"delete"`. This needs a new Alembic migration on top of the current true head (see Constraints).

**Save path note (frontend):** SC saves don't call the backend directly from the form — `useServicesComponents` dispatches `UPDATE_SERVICES_COMPONENT` into the `AgreementEditorContext` reducer (an in-memory edit bundle), committed later by the big save flow in `CreateBLIsAndSCs.hooks.js`. That file already computes `tracksContractModifications`/`awardedEditAppliesDirectly`/`requiresContractModification` and builds the "applies immediately / tracked for next mod" alert copy (`buildSaveSuccessAlert` in `.helpers.js`) for BLI edits. The SC period-of-performance case should fold into that same logic/copy rather than inventing new UI behavior.

**Requirement 2 — lock the SC number on Awarded agreements**

The control is `frontend/src/components/ServicesComponents/ServicesComponentSelect/ServicesComponentSelect.jsx` — a plain `<Select>` wrapper used only inside `ServicesComponentForm.jsx` (line ~112) to set `formData.number` (and resets `optional: false` on change). This is literally the SC's own `number` attribute (SC1/SC2/etc.), confirmed distinct from `AllServicesComponentSelect.jsx` (used in `BudgetLinesForm.jsx` to pick which existing SC a *budget line* links to via the BLI's `services_component_id` FK — a different control, different field, out of scope here).

`ServicesComponentForm.jsx` already has a disabled-condition expression on the number input (line ~145: `formData?.number === 0 || formData?.number === 1 || formData?.number === ""`) — extend it with an Awarded+tracked gate, and have `ServicesComponentSelect.jsx` accept/forward a `disabled` prop to the underlying `Select` (it doesn't today). The gating boolean should reuse the `tracksContractModifications` concept already computed in `CreateBLIsAndSCs.hooks.js`, threaded down through `ServicesComponents.jsx`/`.hooks.js` → `ServicesComponentForm.jsx` as a new prop (none of these currently receive agreement-awarded state).

**Backend enforcement (required — not optional):** `ServicesComponentService.update()` has no Awarded-agreement check of any kind today — only `_check_pre_award_lock` and `_check_not_in_review`. A non-superuser can currently rename an SC's `number` on an Awarded agreement with zero tracking, zero approval, zero record. Add a guard in `update()`: if `agreement_tracks_contract_modifications(services_component.agreement)` and `updated_fields.get("number") != services_component.number`, raise `ValidationError({"number": [...]})`, mirroring the existing `id`/`agreement_id` immutability checks already in `update()` (lines ~155-159) — i.e. reject the whole PATCH, not a partial-field drop, consistent with existing precedent and feasible in the UI since `ServicesComponentSelect` and `PeriodOfPerformanceFields` are separate sibling elements in the same form (so locking the number field alone still leaves period-of-performance editable per Requirement 1).

### Decisions (resolved 2026-11-16)

1. **Requirement 1 — `field` naming granularity: two separate cards (reversed from an earlier, incorrect "combined" decision).** Per the Figma mock (confirmed 2026-11-16), a `period_start` change and a `period_end` change on the same SC each get their own `ContractModificationEdit` row and their own card in the "Edits That Require a Contract Modification" list — not merged into one combined row/card. The "Change To" column label is `PoP-Start` for a `period_start` edit and `PoP-End` for a `period_end` edit (add these to `convertCodeForDisplay`'s `changeToTypes` map, matching the existing `amount`→`"Amount"`, `can_id`→`"CAN"` entries). This matches the original approach already described above (`record_services_component_edit` called once per changed field) — the new partial unique index (`ix_contract_modification_edit_one_pending_sc_field`) keys on `(services_component_id, field)`, so `period_start` and `period_end` are two independent pending rows, each individually guarded against the double-click race, exactly like the BLI precedent's separate `amount`/`can_id`/`date_needed` rows.
2. **Requirement 2 — scope of "SC number": also locks `optional`/`sub_component`.** The backend guard in `ServicesComponentService.update()` must reject the whole PATCH if `number` **or** `optional`/`sub_component` changes while `agreement_tracks_contract_modifications()` is true — not just `number` in isolation. This matches how `ServicesComponentSelect`'s `onChange` already conflates `number` and `optional` on selection, so locking only `number` would have left a side-door open via `optional`/`sub_component`. Update the frontend disabled-state to cover whatever control(s) can change `optional`/`sub_component` too, not just the number select itself.
3. **Requirement 2 — superuser bypass: yes, superusers are exempt.** Matches every other Awarded-agreement lock in this feature family (`sc_requires_approval_gate`, pre-award locks, etc.) — the backend guard should allow a superuser to still change the SC number/optional/sub_component on an Awarded agreement, same bypass pattern as elsewhere.
4. **Requirement 2 — whole-PATCH vs partial-field rejection:** confirmed, reject the entire request (matching the existing `id`/`agreement_id` immutability checks) rather than silently dropping just the locked field(s).

- **Tests required for this class of change:** Per `docs/REVIEW.md`, money math, authorization, migrations, workflow state, and data writes all require a test that actually exercises the change; a missing or ineffective one is S1. Both requirements fall squarely in that bucket (workflow-state tracking for req 1, authorization/data-write blocking for req 2).
