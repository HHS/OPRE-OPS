# Login page & footer styling update

## Goal

Update the OPS login page background and footer styling to match the refreshed Figma design — the background change is actually app-wide (not just the Login page), while footer styling updates apply wherever Footer renders — without affecting login/auth flow behavior.

## Acceptance Criteria

- [x] Login page background color matches the updated Figma design
- [x] Footer styling matches the updated design
- [x] Change works across supported viewports/responsive breakpoints
- [x] No regression to the login/auth flow

## Technical Details

### Approach

Pulled the real spec from Figma via the MCP server (file `dsQFe6G2KjcTWNq7NNZujm`, node `36712:59056`). Confirmed values:

- App-shell gutter background: `#F2F7FC` (replacing `#F0F0F0` / `bg-base-lightest`), applied via a new scoped class `.bg-ops-shell` on the outer wrapper divs in `DefaultLayout.jsx` and `Login.jsx` only — a global retheme of the `base-lightest` USWDS token was evaluated and rejected because it's reused in ~20 unrelated files (nav dropdown, cards, hover states) that Figma does not show changing. Verified the global-retheme alternative compiles cleanly (`$theme-color-base-lightest: #f2f7fc` in `_uswds-theme.scss`) in case UX wants it reconsidered later — not applied.
- Login's inner content column changes from `bg-base-lightest` (gray) to `bg-white`, matching the white-main-on-colored-shell pattern `DefaultLayout` already uses.
- Sign-in card (`MultiAuthSection`) background becomes `#F5F5F5` with no border (was `bg-white` + `border-base-lighter`) — reused the existing `--base-light-variant` token via `bg-brand-base-light-variant`.
- Sign-in buttons needed an explicit `bg-white` — USWDS's default `.usa-button--outline` background is `transparent`, which let the `#F5F5F5` card color show through the buttons instead of rendering white as in Figma. Scoped to only the 3 real sign-in buttons (Login.gov/HHS AMS/FakeAuth trigger), not the 7 unrelated FakeAuth user-selection modal buttons that share the same class string.
- Figma's footer mockup also showed a new "Documentation / Features / Getting started / About us" link row with no real destinations — treated as designer placeholder and explicitly out of scope for this story.
- **UX follow-up (direct request, supersedes the Figma mockup's "Name of Agency" placeholder):** removed the footer's agency section entirely — deleted `AgencyInfo.jsx` and its `usa-footer__secondary-section` wrapper from `Footer.jsx`, the `Login.test.jsx` assertion for "OPRE Portfolio Management System" text, and the "agency information" mention in `Footer.stories.jsx`'s description. (A `.bg-footer-agency` SCSS class had briefly existed for this section's styling earlier in the same session, before the removal request — it was deleted along with the rest of this cleanup and never appears in git history, since it was added and removed within the same uncommitted working tree.) Ran a dead-code sweep (grepped `AgencyInfo`, the removed text, `usa-footer__secondary-section`, `logo-iomg.png`, `bg-footer-agency` repo-wide) — no other orphans found; the `logo-iomg.png` asset AgencyInfo referenced didn't even exist in `public/`, so it was already a dead reference.
- **Found via live verification, not initially caught:** Login's `<header>` had `usa-header--extended bg-brand-primary` — a class meant for the authenticated Header's secondary nav row, which Login doesn't have. Since `<header>` spans full viewport width while the inner white navbar box is centered, this painted a solid brand-blue bar across the top of both gutters that doesn't exist in Figma. Removed `bg-brand-primary` entirely (parent `.bg-ops-shell` pale blue now shows through consistently, matching Figma). Also found the inner content wrapper (`<div className="bg-white">`) wasn't width-constrained, so it painted white across the full viewport below the header, hiding the gutters entirely past that point — moved `bg-white` onto the actual `grid-container` section instead (mirroring `DefaultLayout`'s `<main className="grid-container bg-white ...">` pattern), confirmed via Playwright pixel sampling (`#F2F7FC` consistently top-to-bottom in both gutters after the fix).
- **Dev workflow gotcha hit during this story:** this repo's `bun run start` (Vite) does **not** watch/recompile SCSS — `src/uswds/css/styles.css` is a static file regenerated only by `bun run uswds:update` (`gulp compile`). SCSS edits silently had no effect in the browser until that was run manually. Worth calling out in frontend docs if not already known.
- **Same blue-bar bug existed app-wide, not just on Login (per developer follow-up):** the authenticated `Header.jsx` (used by `DefaultLayout` on every logged-in page) had the identical pattern — `usa-header--extended bg-brand-primary` on the full-width `<header>`, plus a second full-width `<nav className="usa-nav bg-base-lightest">` strip (old gray, not even the new blue) outside its centered white `usa-nav__inner` box. Figma's header (both the logo row and nav-links row) is a single plain-white box with no colored bands at any width. Removed `bg-brand-primary` from `<header>` and `bg-base-lightest` from `<nav>`; verified via Playwright pixel sampling after logging in as System Owner — `#F2F7FC` reads consistently in both gutters from the top of the header down through the page body, no colored bands anywhere.
- **Nav border-top follow-up (developer request):** USWDS's `.usa-header--extended .usa-nav` rule draws its `border-top` across the full-width `<nav>` (1425px in testing), spanning the gutters on both sides. Figma only shows the line under the centered content. Added `.usa-header--extended .usa-nav { border-top: none; }` override in `_uswds-theme-custom-styles.scss` (same specificity, later in source order so it wins) and moved the border onto `.usa-nav__inner` (already width-constrained to 1024px) via `border-top border-base-lighter` utility classes. Verified via computed-style check: `<nav>` border is `0px none`, `.usa-nav__inner` border is `1px solid #DFE1E2`.
- **Second nav border follow-up (developer request):** USWDS also auto-adds `border-top` to whatever immediately follows a `usa-header--extended` via `.usa-header--extended + .usa-section, .usa-header--extended + main { border-top: ...; }` — here `<main>` is Header's next sibling in `DefaultLayout`, so this drew a second divider line directly below the nav row. This one was already width-constrained correctly (border-top and grid-container on the same `<main>` element), but Figma's header has no line there at all, so removed it entirely via `.usa-header--extended + main { border-top: none; }`. Verified: `main`'s computed `border-top` is now `0px none`.
- **Gap follow-up (developer caught a regression from the fix above):** removing `main`'s border-top outright let its first child's top margin (e.g. the page `<h1>`'s `margin-top-4`, 32px) collapse *through* `main` (which has no padding-top) — standard CSS margin-collapsing, since a border is one of the few things that blocks it. That pushed `main`'s own white box down by 32px, exposing `.bg-ops-shell`'s pale blue behind it — i.e. a visible gap in the wrong color, not simply "no gap". Fixed by keeping the border but making it transparent (`border-top: 1px solid transparent`) instead of `none` — same visual result (no visible line) but still contains the margin inside `main`'s white box. Verified: gap between nav and main is `0px`, confirmed via screenshot. Only affects `DefaultLayout`/`Header` (Login's header isn't immediately followed by `<main>` in the DOM, so this selector never matched there).
- **Footer gutter mismatch follow-up (developer request):** `DefaultLayout` renders `<Footer />` *inside* `.bg-ops-shell`, so the gutters beside the "Return to top" row stay pale blue, consistent with the header/main above it. `Login.jsx` rendered `<Footer />` as a sibling *outside* the shell div (leftover from before the background work), so its gutters fell back to plain white — a visible mismatch against the rest of the Login page. Moved `<Footer />` inside the shell `<div>` to match `DefaultLayout`'s structure exactly, which also let the now-unnecessary wrapping `<>...</>` fragment be removed. Verified via pixel sampling: `#F2F7FC` consistently on both sides of the "Return to top" row now.
- **Sticky-footer follow-up (developer request):** on any page shorter than the viewport (reproduced by resizing to 1600px/2500px tall on Login and the authenticated Home page), the footer sat at its natural document height instead of the bottom of the screen, leaving a plain white gap below it — `.bg-ops-shell` had no `min-height`/flex setup, a pre-existing gap in the layout that just became visible once the shell had a distinct background color to contrast against. Fixed with a standard sticky-footer flex pattern: `.bg-ops-shell { display: flex; flex-direction: column; min-height: 100vh; }` plus `.bg-ops-shell > main { flex: 1 0 auto; }` so `<main>` absorbs the extra space and pushes `<Footer>` to the bottom. Verified on both Login and the authenticated Home page at tall viewports (gap = `0px` in both) and confirmed normal scrolling behavior is unaffected when content is taller than the viewport.
- **Main/footer gap follow-up (developer caught a regression from the sticky-footer fix):** on Login specifically, `bg-white` lived on the inner `<section className="grid-container usa-section bg-white">`, not on `<main>` itself (unlike `DefaultLayout`, where `bg-white` is directly on `<main>`). Once `<main>` started flex-growing to fill the viewport, the extra space appeared *after* the white section but *inside* `<main>` — and `<main>` itself had no background, so that space exposed `.bg-ops-shell`'s pale blue instead of staying white. Moved `bg-white` from the `<section>` onto `<main>` (section keeps `grid-container usa-section` for width/padding), matching `DefaultLayout`'s pattern exactly. Verified: `main`'s computed background is now `rgb(255, 255, 255)`, and the grown area between the content and the footer renders white with correct pale-blue gutters beside it, confirmed via screenshot.
- **Whole-page-white regression follow-up (developer caught immediately after the fix above):** moving `bg-white` onto `<main>` without also moving `grid-container` there made `main`'s white background span the *full* viewport width again (same class of bug as the original "blue line" issue — `main` itself was never width-constrained, only the inner `<section>` was), wiping out the pale-blue gutters entirely. Fixed by putting `grid-container` on `<main>` as well (removing it from the now-redundant inner `<section>`, which keeps only `usa-section` for vertical spacing) — exactly mirroring `DefaultLayout`'s single `<main className="grid-container bg-white ...">` element. Verified: `main`'s rect is back to `{width: 1024, left: 200.5, right: 1224.5}` with gutters pale blue on both sides, and the sticky-footer behavior from the previous fix still holds (gap to footer and to viewport bottom both `0px` at a 1600px-tall viewport).
- **Page-load flash follow-up (developer-reported):** on refresh, the centered `<main>` briefly rendered narrower than 1024px before snapping to full width. Root cause: `.grid-container` constrains width only via `max-width` + `margin: auto` (confirmed in the compiled CSS — no explicit `width`), so once `<main>` became a flex item (via the sticky-footer change), its cross-axis sizing depended on the flex default (`align-items: stretch`) resolving before the final layout settled, instead of being explicit from the first frame. Fixed by adding `width: 100%` to the existing `.bg-ops-shell > main` rule. Verified empirically, not just by inspection: injected a `requestAnimationFrame` sampler via `page.addInitScript` that records `main`'s rendered width every frame from navigation start — every captured sample (from the first frame `main` exists in the DOM onward) was already `1024px`, no narrower frame observed.
- **Adversarial review follow-up:** three parallel agents reviewed the commit for correctness, blast radius, and test/dead-code coverage. Nothing broken; two minor non-blocking items addressed: (1) added inline SCSS comments documenting that the two border-top overrides win only by `@forward` source order (identical specificity to the native USWDS rules they cancel), not real specificity — fragile to a future reorder or USWDS version bump; (2) corrected this doc's earlier claim that a `.bg-footer-agency` SCSS class was deleted as dead-code cleanup — it was actually added and removed within the same uncommitted session, so it never appears in git history (not a fabrication, just imprecise relative to the final diff).
- **Missing header divider follow-up (developer-reported, found via a shared Figma screenshot):** Figma shows a thin `border-base-lighter` divider directly below the OPRE logo row, width-matched to the centered content, separating it from the "Sign in" card. USWDS's `.usa-navbar` explicitly sets `border-bottom: none` at desktop widths (`@media (min-width: 64em)`) — the border only shows on mobile by default, because on authenticated pages the nav row below (which already has its own `border-top` from an earlier fix in this story) serves as that visual divider instead. Login has no such nav row, so it needs its own explicit border. Added `border-bottom border-base-lighter` (plus `padding-bottom-2` for breathing room) directly on Login's `.usa-navbar` div in JSX — scoped to Login only, not a global SCSS override, so the authenticated `Header`'s navbar (which must stay borderless, since its own divider lives on `.usa-nav__inner` instead) is unaffected. Verified: Login's navbar computed `border-bottom` is `1px solid rgb(223, 225, 226)` at `width: 1024` (correctly centered); the authenticated Header's navbar, checked after logging in as System Owner, is unchanged at `border-bottom: 0px none`.
- **PR human review follow-up — real regression found and fixed:** a reviewer (weimiao67) flagged that the "Sign-In Failed" alert on Login overlaps `<header>` instead of appearing below it. Root cause confirmed: the alert container (`position: absolute`, `top` unset) is a *direct* child of `.bg-ops-shell`, which this story's sticky-footer fix made a flex container. Per the CSS Flexbox spec, an absolutely-positioned flex child's static position (used to resolve an unset `top`) is computed as if it were the sole flex item — i.e. at the container's start edge — not by DOM order among siblings. Before the sticky-footer change, `.bg-ops-shell` was a plain block box, so the alert correctly fell into normal flow below `<header>`; after adding `display: flex`, it silently started resolving to the same y-position as the header instead. Verified via an isolated HTML repro using the actual CSS values (header 140px tall, same flex/position rules) — before the fix, the alert box's full height sat inside the header's span; after wrapping `<header>` and the alert container together in a plain non-flex `<div>` (removing the alert from being a *direct* flex child), the alert's top exactly matches the header's bottom, zero overlap. This only affected Login (the only page with this exact DOM shape — an absolutely-positioned alert as a direct child of the now-flex shell).
- **PR human review follow-up — specificity hardening (weimiao67 #5):** rather than relying on `@forward` source order to break the specificity tie with native USWDS rules (as flagged as fragile earlier in this story), compounded both border-top override selectors to `.usa-header.usa-header--extended` (both classes always co-occur on every header in this app, confirmed via grep) — this raises specificity to (0,3,0)/(0,2,1), strictly above the native rules' (0,2,0)/(0,1,1), so the overrides win outright regardless of forward order or a future USWDS version bump. Verified in compiled CSS: `.usa-header.usa-header--extended .usa-nav{border-top:none}` and `.usa-header.usa-header--extended+main{border-top:1px solid transparent}`.
- **PR human review items assessed but not changed:** (1) the sign-in card's missing border / ~1.09:1 contrast (weimiao67 #2) matches Figma's literal design (no border in the fetched Figma node) — a design-intent question for UX, not an implementation bug, left as-is pending that decision; (2) `abbr[title]` lost its `-webkit-text-decoration` prefix in the regenerated `styles.css` (rajohnson90) — confirmed real (diffed against `main`), but traced to `caniuse-lite`/browserslist data drift inherent to running `uswds:update` with current dependencies, not to any SCSS edit in this PR; hand-patching the compiled artifact would just get overwritten by the next regeneration, so left for a separate dependency-drift conversation; (3) duplicated header/logo markup between `Login.jsx` and `Header.jsx` (weimiao67 #4) is real but pre-existing, and extracting a shared component is a bigger refactor out of scope for a styling PR; (4) `bg-white` repeated across 3 buttons in `MultiAuthSection.jsx` (weimiao67 #6) is a minor DRY nitpick, low value to fix now.
